## 第一阶段：最小可用 MVP（1~2 周，单人可完成）

### 🎯 目标

在本地，用户能通过 **命令行** 或 **Swagger UI** 提问，系统从指定 Git 仓库中找到相关代码，并给出带**可追踪来源**的回答（即使前端暂不展示，日志中也要能看到出处）。

### 技术栈

- **前端**：命令行交互（Python `input()` 或 FastAPI 自带的 Swagger UI `/docs`）
- **接入层**：前端直连 Python 服务
- **后端**：由 FastAPI 全权处理
- **Python AI 服务**：
  - FastAPI（`/chat` 接口）
  - Chroma（向量库，本地持久化）
  - LangChain（仅使用 RAG 链，暂不引入 Agent）
- **数据库**：SQLite 可选（本阶段不强制，先忽略）
- **LLM**：本地 阿里云百炼qwen3-max API（from langchain_community.chat_models import ChatTongyi）

### 📝 核心流程（RAG + 总结层）

```
用户输入问题 
  ↓ 
FastAPI 接收 
  ↓ 
Chroma 检索 Top-7 代码片段 
  ↓ 
构建原始上下文字符串（拼接 7 个片段）
  ↓ 
总结模型对原始上下文进行精炼概括（独立 LLM 调用）
  ↓ 
构建最终 Prompt（问题 + 总结后的上下文）
  ↓ 
主 LLM 生成答案 
  ↓ 
返回答案文本 + **控制台打印全部 7 个原始来源（文件路径、行号）**
```

### 🔨 具体实施步骤（含关键优化）

#### 1. 代码向量化入库（离线脚本）

**避免粗暴切分函数**  
使用**简单的函数/类边界识别**（基于正则匹配 `def`、`class`、`function` 等关键字）对代码进行预分割，再交给 `RecursiveCharacterTextSplitter` 做细粒度切分，防止将函数拦腰截断。

**入库流程逻辑**：
- 遍历指定 Git 仓库目录，收集特定后缀（`.py`、`.java`、`.js`、`.ts`、`.go`、`.md`）文件。
- 对每个文件内容，先按语言对应的函数/类头正则表达式进行粗分割。
- 对每个粗分块，使用 `RecursiveCharacterTextSplitter`（块大小 800 字符，重叠 100 字符）进一步切分。
- 为每个切片附加元数据（源文件路径）。
- 使用 `OllamaEmbeddings`（模型 `nomic-embed-text`）生成向量并存入 Chroma 持久化目录。

#### 2. 问答 API 服务（模块化结构）

**项目文件组织**：
- `app.py`：FastAPI 主服务，包含 `/chat` 接口及服务初始化逻辑。
- `utils/summarizer.py`：总结层独立模块，封装上下文构建、总结生成及模型创建逻辑。
- `config.yml`：配置文件，定义 Chroma 检索数量（`retrieval_k = 7`）及总结模型参数（`summarizer.model`、`summarizer.temperature`）。

**服务初始化逻辑**：
- 加载 Chroma 向量库（持久化目录、embedding 函数同索引阶段）。
- 初始化主 LLM（`ChatTongyi`，模型名称与温度参数取自配置文件主模型配置）。
- 初始化总结 LLM（`ChatTongyi`，模型名称与温度参数取自配置文件 `summarizer` 节）。
- 构建 `RetrievalQA` 链，设置 `return_source_documents=True` 以获取检索来源。

**`/chat` 接口处理逻辑**：
1. 接收用户问题。
2. 调用 `RetrievalQA` 链进行检索，获取 `Top-7` 个相关文档片段（`source_documents`）。
3. 调用总结模块的 `build_context` 函数，将检索到的 7 个文档内容拼接为原始上下文字符串。
4. 调用总结模块的 `summarize_context` 函数，将用户问题与原始上下文发送至总结 LLM，获得精炼后的总结文本。
5. 构建最终 Prompt，将用户问题与总结文本合并后送入主 LLM 生成最终答案。
6. 在服务器控制台日志中打印全部 7 个来源的文件路径与片段长度。
7. 返回 JSON 响应，包含最终答案及 7 个来源的元数据列表（为后续前端展示预留）。

**总结模块职责**（`utils/summarizer.py`）：
- 定义总结提示词模板，严格约束仅基于参考资料进行概括。
- 提供 `build_context` 函数，将文档列表格式化为上下文字符串。
- 提供 `summarize_context` 函数，封装总结 LLM 调用过程。
- 提供 `create_summarizer` 工厂函数，用于创建总结模型实例。

#### 3. 测试验证

1. 启动 Ollama 并拉取所需模型（`qwen2.5:7b` 用于主 LLM，`nomic-embed-text` 用于 Embedding）。
2. 执行离线索引脚本，将目标代码仓库向量化入库。
3. 启动 FastAPI 服务（`uvicorn app:app --reload`）。
4. 通过 Swagger UI（`/docs`）或命令行发送测试问题。
5. 观察控制台输出，确认：
   - 检索到 7 条文档片段。
   - 每条片段均附带了明确的文件来源。
   - 最终回答基于总结后的上下文生成。

### 📌 边界说明（非常重要）

| 项目         | 是否包含 | 备注                                                      |
| :----------- | :------- | :-------------------------------------------------------- |
| 多仓库切换   | ❌        | 本阶段仅索引单个仓库，第二阶段通过 Chroma Collection 实现 |
| 前端展示引用 | ❌        | 引用仅在服务器控制台打印，用于内部验证                    |
| 会话历史记忆 | ❌        | 每次提问独立处理，无上下文关联                            |
| 流式响应     | ❌        | 一次性返回完整答案                                        |
| 用户鉴权     | ❌        | 仅本地运行，无权限控制                                    |

**核心目的是：验证“检索 → 总结 → 生成”的增强 RAG 链路在代码库上的有效性，并为后续扩展提供信心。**

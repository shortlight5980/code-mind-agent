# 异步逻辑问题分析

## 概述
本文档记录了 CodeMind Agent 项目中存在的假异步问题，这些问题表面上使用了 `async def` 定义异步函数，但内部实际执行的是同步阻塞操作。

---

## 问题详情

### 1. app.py - 主要问题

| 行号 | 代码位置 | 问题描述 |
|------|----------|----------|
| 63 | `/chat` 接口 | `vectordb.similarity_search(query.question, k=retrieval_k)` - 同步向量数据库检索 |
| 68 | `/chat` 接口 | `agent.execute()` - 同步 Agent 执行 |
| 91 | `/chat` 接口 (非Agent分支) | `context_builder.build_context()` - 同步上下文构建 |
| 119 | `/chat` 接口 (非Agent分支) | `llm.invoke(prompt)` - 同步 LLM 调用 |
| 160 | `/chat/stream` 接口 | `vectordb.similarity_search()` - 同步向量检索 |
| 180-184 | `/chat/stream` 接口 (回退分支) | 同步上下文构建 |
| 197 | `/chat/stream` 接口 (回退分支) | `llm.invoke(prompt)` - 同步 LLM 调用 |

### 2. agent/agent.py - 全同步实现

| 方法 | 问题 |
|------|------|
| `execute()` | 完全同步实现，内部调用 `self.agent.invoke()` |
| `execute_stream()` | 同步生成器，内部调用 `self.agent.stream()` |

### 3. agent/streaming.py - 异步桥接但不彻底

- 使用了 `asyncio.to_thread` 和 `loop.run_in_executor` 将同步代码放到线程池执行
- 这只是**避免阻塞事件循环**，并非真正的异步 I/O
- 本质上还是同步执行，只是多了线程调度开销

---

## 问题本质

这些 `async def` 函数内部没有使用任何 `await` 调用真正的异步方法。FastAPI 会自动将它们放到线程池中运行，但：
- 无法获得真正异步的性能优势
- 高并发下会受到线程池大小限制
- 资源利用率不如真正的异步 I/O

---

## 修复建议

### 方案一：使用真正的异步 API（推荐）
- 使用 LangChain 的异步方法：`ainvoke()`, `astream()`
- 将向量检索等操作异步化
- 使用 `await` 关键字

### 方案二：明确使用同步函数
- 将 `async def` 改回 `def`
- FastAPI 同样支持同步路由函数，也会自动放到线程池
- 代码更清晰，避免"假异步"的误解

---

## 影响范围

- 所有 `/chat` 和 `/chat/stream` 请求
- Agent 执行流程
- 向量检索操作
- LLM 调用
